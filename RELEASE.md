# Как выпускать обновления Wireon

Приложение обновляется само: проверяет канал обновлений через 12 секунд после
запуска и потом раз в шесть часов, качает новую версию в фоне и говорит человеку
две строки — сначала «вышла версия X, качаем 47%», потом «перезапустите».
Никто ничего не скачивает руками. Если нажать «Позже», обновление всё равно
встанет при следующем закрытии приложения.

Смотреть, что происходит, можно в **Настройки → О программе → Обновления** —
там же кнопка «Проверить» и полоса загрузки.

## Короткая версия для тех, кто уже всё настроил

```bash
npm run release:prepare patch   # поднимает версию в двух местах + npm run verify
export GH_TOKEN=ghp_...         # только в окружении, не в файлах репозитория
npm run release                 # собирает и публикует
```

Всё остальное в этом файле — про то, что стоит за этими тремя строками.

## Что нужно один раз

1. **Репозиторий на GitHub, откуда качать.** Он должен быть **публичным**:
   приватные релизы электрон-апдейтер скачать не может — ему нужен токен, а
   зашивать токен в приложение нельзя. Если исходники держать открытыми не
   хочется, сделайте отдельный публичный репозиторий только под релизы.

2. **Сказать сборке, какой это репозиторий.** Либо `origin` указывает на него:

   ```bash
   git remote add origin https://github.com/<владелец>/<репозиторий>.git
   ```

   либо переменные окружения (удобно, когда релизный репозиторий отдельный):

   ```bash
   export WIREON_GH_OWNER=<владелец>
   export WIREON_GH_REPO=<репозиторий>
   ```

   Переменные важнее remote. Если не задано ни то, ни другое, сборка соберётся,
   но в настройках честно напишет «В этой сборке не указано, откуда брать
   обновления» — лучше, чем зашить выдуманный адрес и получить у людей вечную
   ошибку.

3. **Токен для публикации** — [personal access token](https://github.com/settings/tokens)
   с правом `repo` (для публичного репозитория достаточно `public_repo`):

   ```bash
   export GH_TOKEN=ghp_...
   ```

   Токен нужен только тому, кто собирает. В приложение он не попадает.

## Каждый релиз

1. Поднять версию и прогнать проверку — одной командой:

   ```bash
   npm run release:prepare patch     # 1.0.2 -> 1.0.3
   npm run release:prepare minor     # 1.0.2 -> 1.1.0
   npm run release:prepare 1.2.0     # или явное число
   ```

   Скрипт делает то, что раньше делалось руками и иногда забывалось: пишет
   версию **в оба места** — `package.json` → `"version"` и
   `src/utils/appInfo.ts` → `APP_VERSION`. Забыть второе особенно неприятно:
   сборка проходит, релиз публикуется, а обновление не приходит никому.
   Расхождение ловит и тест `tests/unit/appInfo.test.ts`.

   Первым делом он проверяет, что в `src/data/changelog.ts` есть запись про
   новую версию, и отказывается работать, если её нет. Список «Что нового»
   зашит в сборку, поэтому пустая история никак не проявляется до момента,
   когда её увидит каждый обновившийся. Запись можно (и удобно) написать
   заранее: всё, что выше текущей `APP_VERSION`, в интерфейс не попадает.

   Заодно скрипт печатает, в какой репозиторий уедет релиз и виден ли
   `GH_TOKEN`, и отказывается понижать версию — electron-updater ходит только
   вперёд, и версия ниже текущей публикуется молча и без всякого эффекта.

   Дальше он сам запускает `npm run verify` (~6-8 минут). Если проверка уже
   прогнана, шаг можно пропустить:

   ```bash
   npm run release:prepare patch --skip-verify
   ```

2. Собрать и выложить:

   ```bash
   export GH_TOKEN=ghp_...
   npm run release
   ```

   Токен живёт только в окружении. В файлы репозитория он не попадает и в
   приложение тоже.

   В релиз уедут установщик `Wireon-Setup-<версия>.exe`, `latest.yml` (по нему
   приложение и понимает, что вышла новая версия) и `.blockmap` — благодаря
   последнему обновление докачивает только изменившиеся куски, а не весь
   установщик заново.

   Публикуется **только установщик**, и это не экономия: когда `nsis` и
   `portable` публиковались одной командой, electron-builder создавал релиз
   двумя параллельными запросами, GitHub отбивал второй («Published releases
   must have a valid tag»), сборка падала — и `latest.yml` не появлялся вовсе.
   Внешне релиз при этом выглядел нормально: установщик на месте, а обновления
   не работают ни у кого.

3. Если нужен ещё и портативный exe на странице релиза — отдельной командой,
   после `npm run release` (она собирает только портативную сборку и добавляет
   её файлом в уже созданный релиз; установщик и `latest.yml` не трогаются):

   ```bash
   npm run release:portable
   ```

Релиз создаётся сразу опубликованным, не черновиком: черновики видны только
владельцу репозитория, и обновление не получил бы никто.

## Что стоит знать

- **yt-dlp обновляется сам и отдельно от приложения.** YouTube ломает старые
  версии извлекателя быстрее, чем выходят релизы: часть видео начинает отдавать
  ссылки, которые проходят все проверки и отвечают 403 ровно в момент
  воспроизведения — человек видит «этот аудиоформат здесь не воспроизводится» на
  каждой второй песне. Поэтому приложение раз в двенадцать часов тянет ночную
  сборку yt-dlp в `%APPDATA%\Wireon\bin` и играет на ней; вшитая остаётся
  запасом. Что сейчас в деле, видно в **Настройки → Диагностика
  воспроизведения** рядом с путём к бинарнику. Сеть недоступна — играем на
  вшитой, как раньше.
- **`npm run release` перед сборкой обновляет вшитый бинарник** (`npm run
  refresh:ytdlp`, канал nightly). Это про первые секунды после установки, пока
  приложение не скачало свой. Без сети шаг молча пропускается и сборка идёт
  дальше — выпустить релиз офлайн по-прежнему можно.
- **Портативная сборка (`Wireon-Portable-*.exe`) сама не обновляется** — у неё
  нет установщика, и лежать она может где угодно. Приложение это видит и пишет
  прямо: для автообновлений нужна установленная версия.
- **Установщик не подписан.** При первой установке Windows покажет
  предупреждение SmartScreen — это про отсутствие сертификата, а не про
  обновления; сами обновления проверяются по sha512 из `latest.yml`.
- **В dev-режиме обновления не проверяются** (`npm start`) — обновлять там
  нечего. В логе главного процесса это видно строкой
  `[Updater] Auto-updates are off: …`.
- **Не GitHub.** Если релизы будут лежать на своём сервере, соберите папку в
  таком же виде (`latest.yml` + установщик) и укажите приложению адрес:

  ```bash
  export WIREON_UPDATE_URL=https://example.com/wireon/
  ```

  Переменная читается при запуске приложения и заменяет канал целиком.

## Как убедиться, что работает

1. Собрать и установить версию `1.0.0`.
2. Поднять версию до `1.0.1` и опубликовать:
   `npm run release:prepare patch && npm run release`.
3. Открыть установленную `1.0.0` и подождать — или нажать «Проверить» в
   настройках. Сверху появится строка «Вышла версия 1.0.1 — качаем, 47%», а
   когда пакет догрузится, она сменится на «Wireon 1.0.1 уже скачан —
   перезапустите приложение».
4. Нажать «Перезапустить»: приложение закроется, поставит обновление и
   откроется снова уже новым.

**Почему обновления могли не приходить раньше.** Механизм был цел, а канал стоял
на `1.0.0`: версия `1.0.2` была собрана локально, но `npm run release` с токеном
так и не запускался, поэтому в `latest.yml` на GitHub лежала прежняя версия.
Установленные копии добросовестно спрашивали канал, получали «у вас последняя» и
молчали. Опубликованный релиз — обязательный шаг, локальная сборка сама по себе
никому ничего не отдаёт.
